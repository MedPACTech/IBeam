# Management lifecycle consumer handoff

Build on the [baseline frontend prompt](../../samples/Management.Bootstrap/docs/baseline-app-prompt.md).
Keep one normal support password/MFA session and use the assigned-app selector. The browser calls
the support API only; machine keys and signing material remain on that backend. Clear app state
on selection changes and discard protected results on revocation. A customer JWT is not a support
session. Existing diagnostics-only and Identity-only hosts remain valid compositions.

## Optional portal composition

The package-only bootstrap defaults `ManagementHost:LifecyclePortal:Enabled` to false. Explicitly
enabling it installs registered-operation availability, licence/seat, export, purge and bulk invite
portal routes. Configure `IBeam:Management:Operations:Portal` with an explicit issuer, 10–60 second
lifetime, persistent private 32-byte base64 `OperationIdKey`, and exact application/audience pairs.
Supply `IManagementActorSigningKeyProvider` through the protected backend composition. No keys
are generated by this flag. See [the signed dispatcher configuration](registered-operation-dispatch.md).
An enabled but incomplete configuration fails startup rather than serving pretend capabilities.

This flag installs no target workers/providers, app data, machine grants or support assignments.
It does not make synthetic loopback targets valid registered-operation network destinations. Real
connected targets require approved public HTTPS origins, DNS/socket pinning and TLS. The existing
three-app loopback demo remains an Identity/ownership demo; full lifecycle examples run in the
isolated package-only integration fixtures with real scoped proofs and durable private stores.

Call `GET /api/management/applications/{applicationId}/operations` for the registered-operation
availability view. Also use `/customer-management` for the older native Identity capabilities.
Render only installed, available operations with current permission. Missing adapters, absent
grants, disconnected apps and incompatible versions are unavailable states, not permission to
fall back to another operation. Registration and discovery never grant authority. See the typed
availability DTOs in the live API document; do not turn this into an arbitrary URL/body proxy.

## Frontend actions

Below, `T = /api/management/applications/{applicationId}/tenants/{tenantId}`.
Every write uses the exact current native `If-Match` and a stable `Idempotency-Key` for its intent.
Preserve keys, versions, body, original operation ID and returned Location after uncertain replies.
Read-only polling does not repeat mutations, send invitations, resume purge or rerun app hooks.

| Action | Portal route | Independent operation and contract |
| --- | --- | --- |
| Owners | GET `T/ownership` | `management.identity.owners.read`; authoritative current owners, never deprecated `Tenants.OwnerUserId` |
| Transfer | POST `T/ownership/transfers` | `management.identity.owners.transfer`; exact ownership version and source/destination membership versions; discover eligible users separately |
| Licence status | GET `T/licenses/{licenseId}` | `management.licenses.read` |
| Suspend / restore | POST `T/licenses/{licenseId}/suspend` or `/restore` | `management.licenses.suspend` / `.restore` plus `.read`; body `{}` |
| Seats | GET `T/licenses/{licenseId}/seats` | `management.seats.read` |
| Assign seat | POST `T/licenses/{licenseId}/seats/assign` | `management.seats.assign` plus `.read`; `{userId}` |
| Unassign seat | POST `T/licenses/{licenseId}/seats/unassign` | `management.seats.unassign` plus `.read`; `{userId,assignmentId}` |
| Export | POST `T/exports`, GET `T/exports/{jobId}` | `management.tenants.export`; submit `{policyKey}` |
| Purge preflight | POST `T/purge-plans` | `management.tenants.delete`; `{policyKey}`; inventory/version/expiry bound to original person and scope |
| Purge confirmation | POST `T/purges`, GET `T/purges/{jobId}` | Same delete grant; confirm `{policyKey,planId,confirmationBinding}` using a distinct confirmation key and explicit human confirmation |
| Bulk revoke | POST `T/invitation-revocations/{batchId}` | `management.invites.bulk-revoke`; `{invitations:[{inviteId,expectedVersion}]}`, 1–50 unique selections and exact native tenant version |
| Bulk receipt | GET `T/invitation-revocations/{batchId}/operations/{operationId}` | Same current bulk authority and original scope/person; never performs work |

Licence/seat receipt routes append `/operations/{operationId}?operation={originalFullOperation}`
to the respective root. Unknown writes return 202 and keep the original operation. A native
receipt proves only its stated transition. Ownership uses its protected tracking reference and
original operation authority. See [ownership](ownership-consumer-migration.md),
[licences](license-status-management.md), [seats](seat-management.md),
[export](tenant-export.md), [purge](tenant-purge.md) and [bulk revoke](bulk-invitation-revocation.md)
for complete DTOs, constraints and recovery rules; the live installed document is authoritative.

Export acceptance is distinct from completion and customer delivery. Show coverage including
retained/excluded categories, expiry, partial/failed/unknown and delivery state. Support receives
metadata only: no bundle download, recipient address, signed URL or customer business bytes.
The app owns export consistency and authorized customer delivery. Purge requires app-owned
cleanup plus all native/app request/write fences. Show inventory before confirmation, retain
coverage after success and never offer a global-account delete. Unknown purge remains unknown
until authoritative reconciliation; no new confirmation or support HTTP resume shortcut.

Bulk revoke reports each canonical child operation with revoked/already-revoked, not-eligible,
changed-version, pending, failed or unknown. Complete with skipped items can still be partial.
Continue only the exact original batch/intention; a new batch is a deliberate new action.
Acceptance races must not revoke accepted membership. No invitation emails are sent by this operation.

## Migration and app hooks

Replace borrowed `tenants.status` for licence actions, `memberships.manage` for seats and
`roles.assign` for ownership with the independent operations above. Existing assignments and
machine credentials gain no new grants. Roll out compatible all-writer fencing before enabling
native mutation capabilities; do not mix upgraded conditional writers with unprotected legacy ones.
The role service preserves owner safety independently of last-administrator protection.

Use `IManagementTargetOperationSender` for typed allowlisted app management contracts. Its fixed
descriptor, schema fingerprint, scope, fresh live capabilities and independent grants are required.
Remove duplicate request signing/proxy code only after equivalent typed contracts and target
handlers are installed; there is no free-form app-route endpoint. Original uncertain write IDs
survive transport failures; only the authorized receipt path reconciles them.

Native role/membership/ownership events are durable at-least-once metadata notifications. Consumers
deduplicate original event IDs and re-read authoritative current native state before updating an
app projection. Delivery does not prove the projection changed. Trusted repair is app-local and
bounded; there is no generic support repair endpoint and `roles.assign` grants none. Projection and
purge must share the app write fence. The synthetic projection store demonstrates this boundary.

Subscribe nonblocking observers to DiagnosticListener/Meter `IBeam.Management.TargetOperations`.
The event is `target.operation.completed`, counter `management.target.calls` and duration histogram
`management.target.duration`. Correlate canonical operation and original safe IDs; never record
headers, tokens, bodies, business data or provider exception text. See [sender](target-operation-sender.md),
[telemetry](target-operation-telemetry.md), [events](membership-lifecycle-events.md) and
[projections](membership-projections.md). Audit completion is not customer business completion.

## Release gate and deployment preparation

This card validates private generated packages; it does not publish a stable version. Run the full
fresh NuGet-only consumer matrix at feature completion, package inspection, isolated portal/target
smoke and package-only bootstrap password/MFA/ownership tests. Preserve existing passwords,
keys, app IDs, statuses and changed/revoked assignments on repeat setup. Development Swagger
at `/swagger` uses `/openapi/v1.json` and the loaded package version; neither document nor UI is
mapped outside Development. Never paste machine keys into Swagger's support Bearer control.

Prepare a coordinated release through the repository release workflow after approval. Verify the
exact versioned graph and required CI, then publish the approved package set. Consumers update
matching versions together, migrate dedicated preprovisioned stores/retention/protection keys,
deploy all participating native/app fences, install target policies/hooks/workers and only then
explicitly enable operation grants and portal routes. Test opt-in and failure states in an isolated
environment before any production deployment. Customer-specific data adapters remain consumer
work; the fixtures are not a production Qurvia purge/export implementation. Rollback must preserve
durable jobs/receipts/enrollment and fences; do not downgrade active fenced writers to old code.
