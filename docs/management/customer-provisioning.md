# Approved roles and customer provisioning

IBM-0109 adds target-only invitation-based provisioning. Portal mirrors and lifecycle forwarding follow in IBM-0111; explicit invitation resend/revoke follow in IBM-0110. Customer acceptance remains in the application's existing Identity API. No customer account table or database connection is added to the portal.

Register `AddIBeamManagementCustomerProvisioningApi(configuration)` in the target with its existing machine authentication, delegated actors, operation/audit stores and native Identity stores. For catalog-only exposure use `AddIBeamManagementAssignableRolesApi(configuration)`. Register `AddIBeamManagementAzureTableAssignableRoles(explicitIdentityRoleTable)` and the existing bounded invitation read repository against the **same target Identity tables** used by native stores. Register `AddIBeamManagementAzureTableCustomerProvisioningStore(dedicatedJournalTable)`. Provision tables administratively; these adapters never create schema.

Configure `IBeam:Management:CustomerIdentity:Provisioning:Policies` as host-owned keys mapped to existing tenant-local role names, for example `default: [Member]` or `enterprise-admin: [Administrator]`. Up to 16 keys, eight names per key and 32 distinct names are supported. Names must be bounded, exact and wildcard-free. Support/Management role names are reserved. The native Azure default privileged roles are `Owner` and `Administrator`; policy never invents or creates roles. No Billing, Licensing, customer profile or external service is required.

| Endpoint | Authority | Contract |
| --- | --- | --- |
| GET `/api/management-identity/tenants/{tenantId}/assignable-roles` | `management.identity.roles.read` | IBeam data array of tenant ID, role ID, name and host policy keys |
| POST `/api/management-identity/tenants/{tenantId}/users/provision` | `users.provision` + `invites.manage` + `roles.assign` | Strict `{ email, policyKey, roleIds }`, stable Idempotency-Key |

All operation names above have the `management.identity.` prefix. `roles.read` is a new independent read grant: catalog visibility never grants role assignment or provisioning. Updating packages grants no new rights. Enable it explicitly in host policy, the target machine credential and the support person's app assignment, with the corresponding app-specific delegation ceiling. Re-verify the portal connection to refresh cached discovery before assigning/using the new capability. The capability remains optional; older targets simply omit it. General role mutation is a later card.

The role repository performs one bounded projected page in the exact tenant partition and role prefix, filtered to the approved names. It reads no permission JSON, role assignments, descriptions, profiles or global support roles. The catalog validates scope, active state and uniqueness. Requested IDs must belong to the selected tenant and policy. An unknown policy, invented/cross-tenant role, duplicate ID, access-grant payload or caller redirect/password/profile is rejected. A disabled tenant remains readable but cannot be provisioned.

Provisioning creates a pending native email invitation with approved role IDs and password setup required. It does not call the existing eager membership-provisioning path, create a global account, change a password/email, confirm email, select a default tenant or grant membership. The management-aware external adapter reuses native invitation/link/message behavior with separate support actor metadata and no fictitious customer inviter. New and existing customers both prove recipient ownership through the same acceptance flow; a customer existing in another tenant is not silently linked. Native account lookup is target-local and never exposed as a global email search or account-existence response.

An existing active **or disabled** membership in the selected tenant produces a safe 409 and no invitation; use the independently authorized membership workflow for deliberate changes. New and existing accounts without that membership receive the same invitation result. Other tenant memberships and global account state are untouched. Role/tenant/policy denials occur before invitation writes; an authorization loss prevents later output/attempts.

Each processing request reserves a receipt scoped to the fixed tenant route and idempotency key. Its canonical fingerprint includes normalized recipient/policy/approved roles, so changing the body under the same key conflicts. `operation.resourceId` is the affected **tenant**, not a fabricated customer account/invitation. The response's `invitation.inviteId` identifies the native invitation. A private journal derives one stable invitation identity per target realm/app/environment/tenant/recipient/policy; even a new request key reuses that effective invitation and cannot change its role intent. Different support organizations authorized for that target share this deduplication, while their processing receipts remain organization scoped and original actor attribution is retained. A point operation-to-invitation index supports later read-only reconciliation without storing request bodies in receipts.

The journal stores AES-256-GCM recovery input and an HMAC fingerprint in private columns, with immutable scope/creator/operation/times authenticated. It uses separate purposes derived from the stable operation fingerprint key. All target instances must share and retain that secret; rotation requires migration or expiry/purge of outstanding intent state. No plaintext recipient/token, ciphertext or request body enters operation/audit DTOs. Native invitation recipient/framework fields remain in the existing customer Identity table. The initial recovery/invitation lifetime is seven days; expiry is metadata and operators own physical retention cleanup.

Native stable-ID insert and token-index repair recover a crash after invitation persistence. Journal ETags claim delivery before SMTP. A known-unsent pending invitation can resume once; sent/failed/unknown attempts are not automatically resent by provisioning. Unknown SMTP delivery may have reached the recipient. Explicit resend is a separate versioned, rate-limited operation. Expired/revoked intent does not automatically create a replacement invitation. Reusing an expired reservation returns a safe conflict; use the authorized invitation lifecycle/recovery procedure.

Responses are safe IBeam envelopes with processing `operation`, business/delivery `status` and optional invitation metadata (submitted recipient, allowed roles, IDs, dates, state and current native version). Commands normally return 202 and Location for the operation receipt; observed accepted invitations return 200. Delivery status and native invitation state are distinct: a redeemable native row may remain pending while delivery is sent. Provider failure before a confirmed result is a generic 503 and can follow a commit; retry the identical request/key and reconcile before creating anything else. No token, redemption URL, outbox, password, raw provider error or arbitrary metadata is returned. Portal recovery and extended operation projections follow in IBM-0111.
