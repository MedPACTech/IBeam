# Target-owned onboarding policies and initialization

IBM-0114 adds `IManagementCustomerOnboardingPolicy` in the provider-neutral `IBeam.Management.CustomerIdentity` namespace. It returns only enabled host-owned definitions: a stable policy key, an existing local administrator role template, and an optional initializer key. `ConfiguredManagementCustomerOnboardingPolicy` is the default. Register a scoped replacement before `AddIBeamManagementEnterpriseOnboardingApi` to supply consumer-owned policy decisions; it must return at most 32 unique safe keys. No commercial or consumer package is required.

Configure `IBeam:Management:CustomerIdentity:Onboarding:Policies` as key-to-role mappings (for example `enterprise-owner: Owner` or `enterprise-standard: Administrator`). `DisabledPolicyKeys` disables listed configured keys. `Initializers` maps a policy key to an explicitly registered initializer's key. All configuration is target-owned. Native invitation creation receives the approved role template explicitly; it no longer assumes the role is spelled Admin or Owner. Existing member templates remain in `Provisioning:Policies` and are checked by the independently authorized roles catalog and provisioning service. Redirects remain under the native target's `ITenantInviteLinkPolicy`; the portal cannot provide a redirect or implementation type.

Discovery uses signed GET `/api/management-identity/enterprise-onboardings/policies` on the target and GET `/api/management/applications/{applicationId}/enterprise-onboardings/policies` on the support API. Both require `management.identity.onboarding.read`, live app assignment, target capability and the normal scoped connection checks. Only `{ key, requiresInitialization }` is returned. No role template, initializer type, storage location or service URL is disclosed. Unknown, disabled, duplicate or malformed policy definitions fail closed. Mutation authority alone does not grant discovery.

Register `IManagementCustomerOnboardingInitializer` implementations on the target, keyed only by server configuration. A required initializer runs after native tenant creation/extensions and before invitation persistence/delivery. Its typed `ManagementCustomerInitializationContext` contains realm, organization, app, operation, onboarding, tenant IDs and policy key. It contains no customer profile bag, email, password, redirect, support authentication principal or customer credentials.

`ReconcileAsync` must durably report Absent, Applied or Unknown for that stable context. Initialize is called only after Absent, followed by reconciliation proving Applied. Implementations must atomically deduplicate by tenant/operation across concurrent processes and persist all required work; a process can die after an external side effect but before the framework acknowledges it. Unknown never causes a blind second initialization. A missing hook, failed hook, or incomplete reconciliation blocks the invitation and exposes `consumer-initialization-incomplete` at the `consumer-initialization` step. The same create key or explicit onboarding retry resumes the saved intent. Provider exceptions are replaced with safe framework errors. Changing the administrator template or initializer invalidates the saved intent rather than broadening it on retry. Disabling a policy blocks writes but leaves read-only status available.

`TenantExtensionOnboardingInitializer<TTenant>` is an optional bridge over existing `IIdentityTenantExtension`, `IIdentityTenantStore` and `ITenantExtensionStore<TTenant>`. Register it using a target-local factory that supplies the initializer key and stores. Use it only when atomic extension-row creation proves that **all** required initialization completed. It finds an existing row before creating, validates the tenant ID, sends a stable causation ID and sets required, redacted lifecycle delivery with no customer AuthUserId. Multi-step Billing, Licensing, Credits or other integrations must implement their own durable initializer/postcondition; row existence alone cannot prove partial external work completed. Those modules remain optional dependencies of the consuming app.

Initialization journals retain encrypted private input separately from metadata-only receipts and audits; keep their existing recovery key and retention across instances. There is no distributed rollback of customer or commercial resources. A consumer must reconcile committed work and keep failed required initialization blocked until it is recoverable. Separate target Identity realms/storage remain required; an initializer must use the scoped target services rather than opening another app's storage from the portal.

Tests cover Identity-only behavior, two independent consumer policies, live-authority discovery, disabled policy denial, stable recovery, lost acknowledgement, Unknown and missing hooks, policy changes, the native extension bridge, signed HTTP discovery and portal output reconstruction. Existing isolated Azure Table and customer request/refresh regression suites remain mandatory.
