# Tenant activation and deactivation (IBM-0113)

Targets explicitly register `AddIBeamManagementTenantStatusApi(configuration)`; support hosts register `AddIBeamManagementPortalTenantStatusApi(configuration)`. Target prerequisites are the existing conditional tenant administration adapter, durable operation/audit/replay and tenant metadata stores, plus protocol-1 customer request/refresh enforcement described in [membership lifecycle](customer-membership-lifecycle.md). The default Azure Table adapter supplies the new optional `IIdentityTenantStatusConditionalStore`; custom/legacy providers without it fail startup. No customer Identity is registered in the support host.

| Method and target path | Authority | Input |
| --- | --- | --- |
| POST `/api/management-identity/tenants/{tenantId}/deactivate` | `management.identity.tenants.status` | Strict `{}`, exact If-Match, Idempotency-Key |
| POST `/api/management-identity/tenants/{tenantId}/activate` | `management.identity.tenants.status` | Strict `{}`, exact If-Match, Idempotency-Key |

Portal paths replace `/api/management-identity` with `/api/management/applications/{applicationId}`. Tenant read/create/rename and support administrator status confer no status-change bypass. Target host allowlist, machine capability, human assignment and live connection all independently permit the operation; a fresh portal check follows each attempt. Recipient/role/profile/reason/delete/billing input is rejected. Use the tenant directory's current version and retain the original key/body/version for an intentional replay. A refreshed version/new action is a new intent.

The existing `IManagementTenantAdministrationService` delegates to the additive native status lifecycle adapter. Exact tenant ETag merge changes only status, update time and the operation marker, preserving consumer fields and all customer data. Existing tenant extension/lifecycle activation/deactivation hooks run with null customer AuthUserId, separate support metadata, required delivery and safe fixed failures. Hook/event idempotency uses the stable operation ID; consumer hooks must deduplicate and check current state when performing longer-running external effects. Recovery resumes only the still-owned pending transition without writing the tenant again. A known rejected concurrent write releases its own unapplied metadata reservation, never another intent or customer data. The same safeguard also covers tenant rename reservations. Legacy native writes clear stale reconciliation markers.

Deactivation changes no global user, membership, role, default-tenant preference, business record or license/billing state. Reactivation preserves independently disabled memberships/removed roles and does not resume onboarding or reactivate any other account. Required customer authorization checks reject the disabled tenant on the next request/refresh check. The standard JWT adapter uses the tenant version as part of its live stamp, has no authorization cache and a five-second read deadline. Requests already authorized and in flight may complete; newly checked requests fail closed. Reactivation changes the version again, so old access/refresh credentials never regain authority; customers sign in/select the tenant again. Another tenant for the same global user stays independently usable. Custom OAuth/cookie/machine/token handlers must implement the explicit request/refresh integration contract before declaring protocol-1 support.

Management reads and status activation remain available for independently authorized recovery. Provisioning, resend, onboarding invitation creation/delivery and role-changing commands reject a tenant found disabled. Revoking a pending invitation or disabling a membership remains permitted as a narrow recovery action. Native customer invitation create/resend/accept checks tenant activity before account setup or membership work; native bootstrap cannot implicitly reactivate a disabled tenant. Already-running cross-store operations can persist an invitation or membership during a concurrent status transition, but current tenant authorization prevents customer access and no bootstrap code may restore the tenant's status. The customer app's approved link/message policies and acceptance flow remain in place.

Target responses use `{operation, tenant, source, externalReference}`; portal responses use `{tracking, tenant, source, externalReference}` in IBeam envelopes. Successful durable processing returns 200, while uncertain replies retain 202/unknown protected tracking. Polling reads an existing receipt and never retries status writes or lifecycle hooks. If a required hook failed, replay the exact original intent to resume it. Missing reads are not proof of failure; 412 means the expected native version changed and 409 means a conflicting owned intent/state. Errors and metadata audit exclude tenant profiles, request bodies, raw provider/hook exceptions, credentials and protected references.

Verification covers native and signed HTTP activate/deactivate races, stale versions, replay/conflicting intent, strict input and live permission loss; required hook failure/recovery without another native write; consumer-column and other-tenant preservation; disabled membership retention on reactivation; rejection of bootstrap/role/invitation work; and an already-issued customer JWT plus refresh across deactivate/reactivate with an unaffected second tenant. Portal cases cover selected-app versions, independent status grants and all three lost-response reconciliation modes.
