# Tenant provenance and existing signup

IBM-0115 defines `support-provisioned`, `self-service` and `unknown` in `ManagementTenantSources`. Tenant directory DTOs now expose `source`; old targets/rows without evidence default to `unknown`. A support create records `support-provisioned` and its durable creation receipt ID. Rename and status changes preserve provenance. No legacy tenants are rewritten, and lack of management metadata never proves self signup.

Use `AddIBeamManagementTenantProvenance()` on the **target** to register optional `IManagementTenantProvenanceRecorder`. It needs the target's existing native `IIdentityTenantStore`, `IManagementTenantAdministrationRepository`, scoped operation executor and bound target/diagnostics options. It adds no HTTP endpoint or signup mode. Existing Identity signup and extension/lifecycle behavior continues unchanged when this optional integration is absent.

A trusted consumer signup handler, durable event consumer or lifecycle integration can call `RecordSelfServiceAsync(tenantId, creationEventId)` **after it has durable evidence of actual self-service tenant creation**. Persist the event ID in the consumer's durable outbox; retries must reuse it. Do not infer origin from a normal customer principal, tenant name, email, domain, role, URL, or a missing metadata row. Do not copy a public signup/query body's alleged source into this method. A generic tenant-created lifecycle event can also describe support/import creation, so consumers must know its trusted origin before recording self service. No automatic hook classifies all tenant-created events.

The service requires a dedicated nonempty Identity realm and target-owned app/environment binding, verifies that the native tenant exists, and writes only target-local optional metadata using atomic create/exact ETag replace. Repeated same-event calls are idempotent. Conflicting known provenance/evidence is rejected. An explicit trusted backfill may promote a ready `unknown` row with no creation evidence; pending management mutations cannot be interrupted. Its existing external reference and last-operation fence are preserved. Provenance is descriptive metadata and grants no Identity or management authority.

`ManagementTenantAdministrationEntity.CreateOperationId` is the original creation evidence ID: a support operation receipt for support provisioning or a durable trusted creation event for self service. Do not send private signup payloads into it or metadata audits. Existing Source/Phase/LastOperationId/Version fields retain their concurrency and mutation-recovery roles. No new global user, OTP, customer role or membership table is created.

Tenant list enrichment performs at most one scoped metadata point read for each item on the single bounded provider page (maximum 100); detail uses one point read. It never scans additional pages to fill a filtered result or writes metadata while reading. Directory `status`/`namePrefix` filtering and protected continuation tokens retain their existing bounds. Server-side provenance filtering is **not supported** in this version; do not advertise a source query parameter or infer a filter from visible-page totals. The portal reconstructs only the three allowed source values and rejects arbitrary target text.

A management application identifies the target app/environment connection; a support organization groups support people and assignments; a customer tenant belongs to the target Identity realm. They are different scopes. Each target uses its existing Identity tables (or its own separately configured Identity database/container) plus optional management metadata stored under realm/app/environment. Support Identity remains separate from customer Identity even if a host shares a physical storage account. Never point a shared cross-app customer realm at this module. The trusted provenance recorder does not create an organization, support assignment or customer membership.

Ordinary password/OTP/OAuth signup, invitation acceptance, MFA, tenant selection and default memberships still use native Identity services. An existing verified customer accepts an enterprise invitation into the same global account and receives only the destination tenant's approved roles; another tenant's Owner/Administrator roles are not copied. Enterprise external invitations do not force a new default tenant. No management key or support login is needed for normal customer signup or customer invitation acceptance. See also the onboarding, invitation and customer access-enforcement contracts.

Verification includes trusted-record replay/conflict checks, support provenance and rename preservation, bounded read-only enrichment, no public source input, portal projection, concurrent actual Azure Table writes and overlapping tenant IDs across two isolated storage instances, plus the normal signup/auth/invitation suites.
