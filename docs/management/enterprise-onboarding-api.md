# Enterprise onboarding API

IBM-0108 installs the opt-in HTTP/portal adapters for [onboarding services and recovery](enterprise-onboarding.md). No customer Identity connection is registered in the support portal.

Target: `AddIBeamManagementEnterpriseOnboardingApi(configuration)`, alongside the target machine-auth/delegation dependencies and stores documented for IBM-0107. Portal: `AddIBeamManagementPortalEnterpriseOnboardingApi(configuration)`. These registrations include tenant-administration and operation-polling prerequisites. Target policies/machine grants must explicitly enable `onboarding.create`, `onboarding.read`, `onboarding.retry`, `tenants.create`, `invites.manage` and `roles.assign` as appropriate. General customer provisioning/invite/role routes follow in IBM-0109–0111; these initial invitation/role capabilities are the restricted onboarding adapters.

| Action | Target | Portal |
| --- | --- | --- |
| Create | POST `/api/management-identity/enterprise-onboardings` | POST `/api/management/applications/{app}/enterprise-onboardings` |
| Status | GET `/api/management-identity/operations/{operationId}` | GET `/api/management/applications/{app}/operations/{operationId}?authority=management.identity.onboarding.read` |
| Explicit retry | POST `/api/management-identity/enterprise-onboardings/{operationId}/retry` | POST `/api/management/applications/{app}/enterprise-onboardings/{operationId}/retry` |

Create requires a stable `Idempotency-Key` and a strict JSON object with `tenantName`, `initialAdminEmail`, `policyKey` and optional `externalReference`. The policy key must be host approved; names/roles/redirects/passwords/profiles cannot be added through extra JSON fields. Retry accepts **only `{}`**, a stable new retry intent key and an existing onboarding operation ID. It cannot change the recipient, policy, tenant or external reference. Retry requires `onboarding.retry` and every create prerequisite; read requires its independent current grant. A completed business operation returns its existing result without another tenant, invitation or delivery.

All responses use IBeam envelopes (`success`, `data`). Target commands return an operation receipt with optional `onboarding` and a Location for operation polling. Portal commands return protected `reference`, business `status`, optional validated `operation` and reference `expiresUtc`, with a Location for same-authority polling. Commands return 202 while incomplete or uncertain and 200 when customer acceptance is complete. Known operation reads return 200; protected reference polls return 202 until business completion. Tenant writes preserve their existing response semantics.

`operation.status = succeeded` means the setup attempt was processed. **Use `operation.onboarding.completed`/`status` for business completion.** The nested object contains original operation ID, onboarding ID, tenant ID when known, invitation ID, step, delivery status, fixed error code and dates. No request fields, private journal ciphertext, native invitation token/link, password, SMTP error or outbox data is returned. `nextAction` is a conservative `poll`, `await-customer` or `none`; it never implies retry authority. A frontend may offer an explicit retry only with the independently effective retry composite grants, and must handle live denial.

The query service enriches receipts from authoritative invitation, verified intended customer and active approved membership state. It performs no recovery writes and sends no email. New and existing customers accept through the application's normal Identity invitation flow. Expired/revoked/wrong-recipient invitations cannot produce completed business status. Tenant setup and mail-delivery failure remain distinct; unknown SMTP delivery may already have reached the recipient.

The portal sends one fixed-path HTTPS write attempt with exact method/path/body/idempotency binding and a fresh signed actor assertion. The original customer principal is never forwarded. Read/retry always recheck current assignment, app/connection, realm, target machine grant and host policy. Retry's receipt lookup and write share one outbound deadline; a fresh authorization budget remains for the final access check. No general HTTP policy blindly retries writes.

If the portal loses a response after commit, it returns 202/unknown with an encrypted short-lived reference rather than claiming failure. Follow Location using the same authority to resolve the existing receipt without sending the command again. References bind the support person/org, app/environment/realm, credential/connection and operation; another app/user cannot replay them. They contain only protected intent identity, never the create body or recipient. Once the operation ID is known, a separately authorized reader can use the GUID status route. After reference expiry, re-submit the identical original request/key under current authority, or poll the known GUID. A missing receipt/journal is not permission to automatically create another enterprise.

Same-intent changed input returns 409; invalid/extra fields return a safe 400; missing/revoked authority denies access; unavailable/malformed/oversized target responses become unknown or generic service failures. Only allowlisted status/error values and scoped IDs are reconstructed. Existing diagnostics-only targets and custom adapters retain their earlier behavior; onboarding operations require installed modules and receipt protocol 1. Metadata audit records operation/outcome, actor, app and known resource IDs without inputs or response snapshots. Journal retention, key lifecycle, explicit at-least-once mail recovery and delivery-attempt bounds remain as documented for IBM-0107.
