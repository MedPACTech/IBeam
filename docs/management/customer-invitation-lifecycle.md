# Customer invitation lifecycle (IBM-0110)

Install this module in the customer target host, alongside the existing named management credential and delegated actor modules. It never registers a management invitation-accept endpoint or a customer principal for support staff. The support portal integration follows in IBM-0111.

```csharp
services.AddIBeamManagementAzureTableCustomerInvitationTransitionStore(privateTransitionTable);
services.AddIBeamManagementAzureTableCustomerInvitationReader(existingNativeTenantInvitesTable);
services.AddIBeamManagementAzureTableAssignableRoles(existingNativeTenantRolesTable);
// Also supply the existing tenant reader, native tenant/invitation services and stores,
// durable operation/audit/replay stores, and user-directory cursor protection key.
services.AddIBeamManagementCustomerInvitationsApi(configuration);
```

The operator creates the dedicated transition table through trusted schema tooling. Runtime reads/writes do not create tables. Transition storage and its encryption key remain target-side. `IBeam:Management:CustomerIdentity:Invitations` requires `ApprovedRoleNames` (existing customer roles, e.g. Member, Owner, Administrator), `MinimumResendSeconds` (default/minimum 60), and `MaximumResendsPerDay` (default 5, maximum 20). The host explicitly allows `management.identity.invites.read` and/or `management.identity.invites.manage` through EnabledOperations and machine capabilities. Human assignments independently grant the requested operation. Merely seeing an invitation grants no mutation permission. Missing conditional native store, delivery adapter, or repositories fails startup; custom providers must implement the additive native conditional invitation port before enabling this module.

| Method and target path | Authority | Input |
| --- | --- | --- |
| GET `/api/management-identity/tenants/{tenantId}/invites` | invites.read | Existing bounded directory query/cursor |
| GET `/api/management-identity/tenants/{tenantId}/invites/{inviteId}` | invites.read | None |
| POST `/api/management-identity/tenants/{tenantId}/invites/{inviteId}/resend` | invites.manage | Strict `{}`, Idempotency-Key, exact If-Match |
| POST `/api/management-identity/tenants/{tenantId}/invites/{inviteId}/revoke` | invites.manage | Strict `{}`, Idempotency-Key, exact If-Match |

Use the full operation names (`management.identity.` prefix). Every call verifies the live machine credential, delegated actor, app/environment/realm and tenant. Mutation headers and the exact empty JSON body are signed. Missing/wildcard/stale versions cannot bypass CAS. The same key, route, action and original version replay one durable receipt; changing the action/version under that key conflicts. Rate limits apply to new resend transitions using native per-invitation persisted counters and the original ETag. Same-key replay never sends again or consumes another rate-limit slot. Return 412 for a changed version, 409 for a claimed/redeemed/revoked or policy-ineligible invitation, and 429 for the server resend limit. Do not reuse one key for a different action.

Resend supports email invitations with 1–8 existing, active, target-allowlisted role IDs. Invitations with legacy role-name resolution, business resource access grants or default-tenant changes are deliberately ineligible for resend; revoke still works. Resend never changes recipient, role IDs, inviter, password-setup requirement or stored redirect. URL/message generation reuses the customer's configured trusted `ITenantInviteUrlBuilder`/link policy. Expired unclaimed invitations can be explicitly resent with a fresh token and seven-day expiry. Revoked/redeemed invitations cannot be reopened. A disabled tenant cannot resend; support can still revoke its pending invitations.

Resend rotates the authoritative native token hash with exact ETag before sending. Old token-index entries cannot authorize acceptance: native lookup refreshes the primary and verifies its exact current hash. An interrupted token-index write is repaired idempotently before any send. Native invite creation/update/resend, revoke, expiration and customer acceptance participate in the same conditional protocol; ETag merge preserves consumer columns. Additive `IBeamInvite*` columns record acceptance claims, last transition, resend window/count and separate management actor IDs, without pretending the support person is a customer inviter/revoker.

After destination verification, ordinary customer acceptance obtains a durable claim bound to that customer before any tenant membership/role assignment. Concurrent acceptance and resend/revoke have one winner. A claim has no stealable timeout; the same verified recipient can resume interrupted acceptance even after expiry. Management cannot override a claimed acceptance. Customer acceptance remains in the existing customer app, including verified email/password challenge, OTP or verified session. Management resend persists the native verification requirement even for an invitation originally created by a customer, so it cannot enable unverified password setup. An expired unclaimed, revoked or superseded token cannot create membership. Customer-owned hooks must remain idempotent during acceptance recovery. There is no support force-unlock endpoint.

Mutation responses use the normal IBeam envelope with `operation`, `status`, and a safe `invitation` projection. Native invitation status and delivery outcome are separate: `sent` does not mean redeemed. Delivery status may be pending, sending, sent, failed (preparation known not sent), unknown (SMTP/acknowledgment uncertain), or superseded. A processing receipt can succeed while delivery is failed/unknown; inspect `status` instead of treating HTTP 200 as confirmed email delivery. A send claim is persisted before SMTP, and replay/polling never automatically sends a claimed/failed/unknown message again. After a lost reply, read the receipt and current invitation; explicitly request a new rate-limited resend with its current version when appropriate. Receipt reads are read-only. Public responses never contain tokens, redemption URLs, private outbox data, link policy or sender credentials.

Recovery stores only metadata plus authenticated encrypted token/version intent in a dedicated per-operation journal, bound to realm/app/environment/tenant/invitation/operation/actor/times. A separate HMAC-derived AES-GCM purpose uses the stable operation fingerprint key. Retain that key and private journal for the seven-day recovery window across restarts/instances. Cleanup is explicit operator work; ExpiresUtc is metadata, not automatic TTL. General receipts retain their configured longer retention, and expired private recovery input cannot be replayed to rotate a token. Keep all raw input/recipient/token/URL out of service diagnostics and metadata audit. The existing read directory still reads one projected provider page (maximum 100), with actor/app/realm/credential/filter-bound protected cursors.
