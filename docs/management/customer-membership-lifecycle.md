# Customer membership and role lifecycle (IBM-0112)

IBM-0122 adds optional [independent tenant owner protection](tenant-ownership-protection.md). Configure native owner roles separately from `AdministratorRoleNames`: a remaining Administrator does not replace the last Owner. This uses the same persisted revision and supported native/management writer paths, without introducing ownership transfer or global account deletion.

The target explicitly registers `AddIBeamManagementCustomerMembershipApi(configuration)`; the support host separately registers `AddIBeamManagementPortalCustomerMembershipApi(configuration)`. Both use existing named management authentication, delegated actors, live assignments/connections and private operation/audit/replay storage. These modules do not register customer Identity in the support host. Unsupported conditional membership providers or missing customer access enforcement fail target startup and cannot advertise a usable adapter.

| Target route (prefix `/api/management-identity`) | Independent authority | Strict body |
| --- | --- | --- |
| PATCH `/tenants/{tenantId}/users/{userId}/membership` | `management.identity.memberships.manage` | `{ "isEnabled": false }` (required boolean) |
| PUT `/tenants/{tenantId}/users/{userId}/roles` | `management.identity.roles.assign` | `{ "policyKey": "default", "roleIds": [] }` |

Portal mirrors use `/api/management/applications/{applicationId}` in place of `/api/management-identity`. Every write requires Idempotency-Key and exact If-Match from the existing user directory's membership version. Read grants remain separate. Role replacement accepts 0–8 existing, active, target-policy-approved local IDs; an empty list explicitly removes editable roles. It never accepts arbitrary role names, global user state, profile data, free-text reasons, passwords, MFA resets or impersonation. Role catalog visibility does not grant role assignment. A role assignment preserves membership enable/disable state. Re-enabling uses the roles currently stored, so it cannot restore roles separately removed while disabled.

Role replacement safety (IBM-0121): the same selected target policy must authorize **every role being removed**, not just the requested roles. A Member-only policy therefore cannot strip an existing Owner or another out-of-policy role by omitting it, even if another administrator remains. Such requests return 403 before reserving a mutation receipt or modifying membership/projection/access versions. For a legitimate replacement across role sets, the trusted host can explicitly configure a policy covering both the removed and requested roles; an Owner-only assignment policy cannot implicitly revoke Member, and a Member-only policy cannot implicitly revoke Owner. No additional `roles.read` or `memberships.manage` grant is required. An otherwise valid request with a stale membership version still returns 412. Names-only legacy roles or a mismatch between stored role names and resolved role IDs return 409 and must be normalized through a trusted native migration; role replacement does not silently rewrite legacy authority. Exact successful replay and recovery after a lost projection response remain supported.

This policy boundary is not an independent last-owner guarantee: an explicitly approved policy can still authorize removing its own Owner role while another configured administrator remains. Independent owner protection and explicit atomic ownership transfer are separate follow-on cards. Do not widen provisioning policies solely to bypass the safety check, or rely on a frontend guard to establish ownership authority.

The target needs its existing native tenant/membership/role stores and the bounded `IManagementAssignableRoleReadRepository`. Configure `IBeam:Management:CustomerIdentity:Provisioning:Policies` as for IBM-0109, and explicitly configure `IBeam:Management:CustomerIdentity:Memberships:AdministratorRoleNames`, e.g. `["Owner", "Administrator"]`. No administrator names are inferred from client input or permission claims. Eligible administrators are enabled native memberships carrying one of these active immutable native system-role IDs (legacy name-only memberships are counted only against these exact immutable names). Consumer policy must select roles that actually provide administrative recovery in that application. Non-system or missing administrator definitions fail closed. New approved immutable administrator roles can expand protection; removing previously protected IDs requires a trusted explicit migration.

`IIdentityTenantMembershipAdministrationService` owns eligibility and lifecycle rules. The optional `IIdentityTenantMembershipConditionalStore` supplies bounded metadata snapshots and conditional persistence. The initial Azure Table adapter supports a maximum 5,000 members per tenant for these administration commands; it reads at most six projected pages within the service's 20-second deadline and fails closed above the bound. Larger/custom providers need a compatible bounded concurrency adapter before enabling this capability. Snapshots select membership IDs, status, roles and version only, never contact/profile data.

Azure Table uses an additive `!IBEAM|MEMBERSHIP` revision/protection row in the existing tenant's TenantUsers partition. It adds no customer auth tables or second customer account database. A management write commits the caller's membership ETag and the tenant snapshot ETag in the same Table transaction. A change to another member invalidates the snapshot, preventing two concurrent disable/demotion requests from removing the final administrator. Every supported native membership writer advances that partition revision. Native grants, bootstrap and role rename/removal participate; immutable system roles cannot be deleted/renamed through the native role store. Raw legacy destructive membership/revoke methods fail closed once protection is configured. The normal native `TenantRoleService` uses the additive administration service when registered. Direct custom writers must use the same conditional port/protocol; out-of-band table edits are trusted operator migrations, not supported concurrent application writes.

The native bootstrap path cannot reactivate a disabled membership. Management does not change a global account, another tenant's membership, the user's stored default-tenant preference, or create/delete customer data. Primary writes preserve consumer columns. UserTenants remains a secondary projection; native membership lookup uses the authoritative primary after a participating writer changes it. Projection failures are explicit and leave one stable operation/primary marker for reconciliation. Recovery repairs current projection state without replaying an older primary change. Unknown/partial outcomes are never silently reported as success or rolled back destructively.

Customer request and refresh enforcement is mandatory before enabling writes. For the standard customer IBeam JWT host:

```csharp
using IBeam.Identity.Api.DependencyInjection;

// After the existing customer Identity/JWT registration; keep support/machine schemes separate.
services.AddIBeamIdentityTenantAccessEnforcementApi(); // Optional explicit customer bearer scheme argument.
services.AddIBeamManagementCustomerMembershipApi(configuration);
```

The standard adapter adds `ibeam_tenant_access_version` at JWT issue/refresh and validates it against current native membership and tenant versions on every customer bearer request. It uses no authorization cache, a five-second provider deadline and fails closed on unavailable state. A committed disable/role change is rejected on the next authorization/refresh check; requests already authorized and in flight may complete. An old refresh cannot reuse old role claims, and re-enable never revives a previously issued token. A customer signs in/selects the tenant again for fresh current claims. Other tenants for the same global user remain independently usable. Tenant metadata changes also advance this version; plan for reauthentication after a tenant rename/status change. Installing the adapter invalidates tenant JWTs issued without the version claim, so include normal customer sign-in in rollout. Existing pre-tenant selection tokens remain usable only at the existing tenant-selection boundaries; business routes must still require a selected tenant.

Bring-your-own authentication, OAuth, cookies, API credentials and alternate token/refresh implementations require an explicit host integration. Call `IIdentityTenantAccessValidator.RequireAsync(userId, tenantId, expectedVersion)` at each selected-customer-tenant authorization boundary; bind the returned version when issuing access/session credentials and reject changed/disabled state during refresh. Do not mint fresh versions around stale role/permission claims. Then register `IIdentityTenantAccessEnforcement` protocol 1 with a bounded non-empty integration mode. That marker is a trusted declaration by host code, never a request/claim setting or permission bypass. The provided automatic API adapter covers the standard IBeam customer JWT issue/refresh path; it does not wire arbitrary OAuth/cookie/machine handlers. Custom hosts must complete their own integration before declaring support. Tenant-scoped credentials lacking current enforcement remain denied by the supplied customer bearer integration. Preserve current issuer/audience/signing-key validation and do not apply this customer scheme hook to the support login or management machine credential scheme.

Responses use the normal IBeam envelope: target `{operation, membership}`, portal `{tracking, membership}`. Membership output is a safe ID/status/role/version projection with no global profile lookup. HTTP 200 means a durable processing receipt succeeded; 202/unknown retains protected same-intent tracking after a timeout or unusable target reply. Polls read existing receipts only. Replay the exact original key/body/version to reconcile a partial write; changed input under that key conflicts. Use a new intent after deliberately refreshing a stale version. 409 covers final-administrator/policy conflicts, 412 covers changed member/tenant snapshot versions, and all errors use fixed safe messages. Metadata audit captures trusted actor/app/tenant/user IDs, allowlisted operations and safe outcomes; no request/profile/exception snapshots are persisted.

Provider and signed HTTP tests force a same-snapshot race across two different administrators, test stale snapshots after native grants, prevent implicit bootstrap reactivation, verify lost projection recovery, preserve consumer/default/other-tenant state, and reject malformed scope rows. A real JWT bearer fixture tests an already-issued token and refresh after both membership disable and role removal, including re-enable, fresh claims and the same user's unaffected second tenant. Portal tests cover independent grants, exact versions, role removal while disabled, lost-response polling and live assignment loss.
