# Enterprise onboarding services

IBM-0107 adds target-side services. IBM-0108 supplies [HTTP endpoints and portal integration](enterprise-onboarding-api.md). The support host does not register customer Identity or a customer connection string.

## Target registration

Install `IBeam.Management.Identity.Target.Services`, the existing Identity services and a durable invitation store. Register `AddIBeamManagementEnterpriseOnboarding(configuration)`, operation/audit stores, tenant-administration metadata and `AddIBeamManagementAzureTableEnterpriseOnboardingStore(dedicatedTableClient)`. Provision the dedicated journal table administratively; runtime code never creates schema. Azure Table's existing `AzureTableTenantInviteStore` supplies the optional `IExternalTenantInviteStore`. Register the existing `ITenantRoleStore`, `ITenantInviteStore`, user and membership stores in the target only. The additive `TenantInviteService` constructor accepts the role store for trusted external role validation; the original constructor remains compatible but does not enable the durable external adapter. Default DI selects the additive constructor when the role store is registered. Unsupported stores or custom invite services must supply equivalent durable external adapters; no capability should be advertised without them. Services alone install no new endpoints/capabilities.

Internal role/invitation lookups use these target-local read stores under the verified Management service boundary. They do not require or fabricate customer service permissions, a customer principal, a default tenant or a global system-authorizer bypass. Customer-side acceptance continues through the normal Identity services and their existing policies.

Configure `IBeam:Management:CustomerIdentity:Onboarding:Policies` as explicit policy keys mapped to `Owner` or `Admin`, for example `enterprise-owner: Owner`. Tenant lifecycle hooks must seed exactly one active target-local role with that name. Missing/ambiguous roles stop before invitation creation. The request accepts only tenant name, initial administrator email, optional external reference and policy key. Callers cannot supply role names/IDs, permissions, passwords, profiles, redirect URLs or customer inviter IDs. Redirects use the application's existing approved invitation link policy. Changing/removing the policy blocks recovery under its old intent; read-only status remains available.

`IManagementEnterpriseOnboardingService.CreateAsync(request, idempotencyKey)` requires the original verified `onboarding.create` authority, including `tenants.create`, `invites.manage` and `roles.assign`. `RetryAsync(onboardingId, newRetryKey)` additionally requires `onboarding.retry` and the complete create matrix. `GetAsync(onboardingId, authority)` accepts onboarding read/create/retry authority with current access checks. The target permits these composite services to call their already-granted prerequisites while retaining the original assertion in its scoped context. Each prerequisite rechecks the complete original machine grant, host policy and installed adapters; it never creates a customer principal. The portal's existing signed-actor issuer requires the same human matrix.

## Durable stages and recovery

- A metadata-only processing receipt reserves the onboarding ID. A separate scoped journal reserves an invitation ID and stores authenticated encrypted recovery input before customer writes. Scope includes support organization, registered app, target realm, app key and environment. Tenant creation uses a deterministic child intent through the existing tenant lifecycle coordinator. Retries reuse the tenant, external-reference reservation and extension lifecycle work.
- `tenant-creation`, `tenant-extensions`, `extensions-completed` and `invitation-persisted` are distinct steps. Missing roles and interrupted setup return safe recoverable state. There is no compensating tenant deletion.
- Invitation creation uses a conditional stable-ID insert. Recovery repairs the separate token index without replacing the primary invitation. Token lookup always rechecks the authoritative primary so a stale index cannot resurrect an invitation. No account, membership, default tenant or role grant is created before acceptance.
- A journal ETag claim precedes email delivery. Delivery is `pending`, `sending`, `sent`, `failed` (preparation failed before invoking the sender), or `unknown`. A crash during sending or failed acknowledgement becomes unknown after the two-minute claim expires. Ordinary create retries do not send again. Explicit retry may resend the same invitation and token after the claim expires. Email is **at least once**: an unknown prior attempt may have reached the recipient. Neither retries nor failed delivery create another invitation or delete the tenant.
- Business status is `in-progress`, `recoverable-failure`, `awaiting-acceptance` or `completed`. A successful processing receipt means the setup attempt finished; it does **not** mean enterprise onboarding completed. Interfaces/UI must use the onboarding DTO's `Status`/`Completed`. Mail delivery alone never completes it. Read-only status checks the authoritative invitation redemption, intended verified customer recipient and active tenant membership containing the approved role IDs. No status poll resumes setup or sends email.
- Customer acceptance uses existing `ITenantInviteService.AcceptInviteAsync`. An external invitation has no customer inviter (`InvitedByUserId = Guid.Empty`), with separate external actor metadata. Existing-session acceptance requires a verified matching recipient; external email/password setup requires the existing verified email challenge. OTP uses existing verification. Support never sets or receives a password, token, invitation URL, OTP or customer session. Existing ordinary invitations/self-signup retain their behavior.

Re-submit the identical create request/key to recover interrupted setup, or use explicit retry with a stable new retry key. Reusing a key with changed input conflicts. Retrying the same retry key does not send another mail. Concurrent journal updates use exact ETags; resolve conflicts by reading current status and retrying the same intent. Role policy changes, revoked authority, expired invitations and unavailable storage never cause a broader fallback or silent replacement invitation.

## Privacy, keys and retention

Recovery input (name, email, reference, approved policy/role and random invitation token) is AES-256-GCM ciphertext in a private journal column, with authenticated immutable scope/IDs/times. Its key derives from the stable operation fingerprint key using the separate `ibeam-onboarding-recovery-v1` purpose. Every target instance must share and retain that secret for the journal's lifetime. Rotating/removing it without migration makes pending recovery unavailable. No plaintext token or request is stored in operation/audit receipts; plaintext native invitation framework fields remain in the existing customer Identity table. Encrypting the journal is not a substitute for restricted table access and secret-store protection.

The initial invitation/recovery window is seven days. Expiry is metadata, not automatic provider TTL; operators must purge expired private journals and tokens according to their retention policy. Operation/audit receipt retention remains independently configured. A replacement invite after expiry/revocation requires a future explicitly authorized invitation workflow, never an automatic resend here. Customer hooks must remain idempotent by operation ID. Logs/audits include scoped identifiers and fixed error codes only; no input, ciphertext, names, recipients, provider error text or credential material.

Delivery attempts are capped by Operations.MaximumAttempts (default 10) per onboarding journal, in addition to each processing receipt's attempt limit. Exhaustion requires operator investigation; creating more retry keys does not reset the mail-attempt counter.
