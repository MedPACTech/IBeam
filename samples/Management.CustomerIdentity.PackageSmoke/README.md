# Package-only customer management verification

Run `scripts/Test-ManagementCustomerIdentityPackages.ps1` from PowerShell 7 with .NET 10 and two private loopback Azurite Table connections in `IBEAM_MANAGEMENT_TEST_STORAGE` and `IBEAM_MANAGEMENT_TEST_SEPARATE_STORAGE`. Both must explicitly target the local devstoreaccount1 account. Never supply production credentials. Outputs default to a unique ignored `_tmp_pkg_smoke/customer-*` directory; `-OutputDirectory` and `-PackageVersion` can select a reproducible private build. `-ReusePackages` skips packing when testing unchanged binaries.

The script builds the Management/Identity dependency closure in Release, packs a single private version, inspects package assets and accidental secret/test content, runs the existing two-target errors/logs sample, then copies the regression **test sources** into isolated consumer directories. Every framework ProjectReference is replaced by a PackageReference to the generated local feed. Neutral build props/targets and a fresh package cache prevent source-tree dependency fallback. Assets are checked to ensure every IBeam dependency has type `package`; skipped/inconclusive checks fail validation. Nothing is published, tagged or deployed.

`EnterpriseWorkflowPackageTests.cs` composes one support TestServer and two customer TestServers backed by independent Azurite instances for tenant, role and membership storage. It deliberately reuses customer and self-service tenant IDs across both stores. Through the portal API it creates an enterprise tenant/admin invitation, proves no initial customer membership exists, invokes native verified existing-customer invitation acceptance, polls authoritative completion, reads the customer directory, provisions/accepts another member, changes roles, tests last-admin rejection, disables the enterprise tenant, preserves the customer's self-service default, and checks live support assignment revocation. Safe audits contain no recipient or token canaries.

This is validation tooling. Existing test assembly identities are retained so the suites can use their internal, fixture-only transport seams. No framework implementation sources are copied. The in-process bridge exchanges fixture proof labels for real scoped RSA actor assertions and uses the target's real named machine authentication; it binds the same support person, organization, selected app and environment. Synthetic verified-user and invitation-delivery adapters avoid sending mail; native acceptance still verifies the account and grants roles through the actual Azure Table membership implementation. Invitation CAS, durable journals, delivery failures and native user/account providers are independently exercised by the provider/regression suites. The test does not claim a deployed network, production mail service or interactive support login. Real support password/MFA/revocation behavior runs in the separate Management.Identity suite; customer JWT/request/refresh enforcement runs against actual JWT middleware and native storage.

The production transport still requires approved public HTTPS, fixed routes, DNS/socket pinning, TLS and no redirects/proxies. No localhost/network exception or anonymous setup endpoint is added. Production consumers register their own public service ports only as documented; the test transport seam is not a deployable adapter.

The complete matrix includes no/wrong authentication, wrong realm and app, human/machine capability ceilings, invalid/replayed assertions, cross-tenant/app cursors, live assignment/key/connection revocation, disabled users/tenants, CAS and last-admin races, durable step crash recovery, unknown SMTP delivery and lost HTTP responses, metadata-only audit, provenance and policy initialization, errors/logs scrubbing, support Identity and ordinary customer signup/auth. See the package-only TRX files and `customer-validation-summary.json` for exact counts. The companion `validation-summary.json` records package closure/content validation and the diagnostic sample.

Azure Table is the tested native query/CAS provider. Other storage providers must supply the optional bounded query and conditional mutation ports before capabilities are advertised. Standard IBeam JWT hosts must install `AddIBeamIdentityTenantAccessEnforcementApi`; custom authentication must integrate the live access validator and explicitly attest enforcement. Protected tenant administrator roles must be configured and immutable. Existing tokens without the required live tenant-version stamp require reauthentication when enforcement is enabled. Preserve recovery encryption/fingerprint keys and retention across instances. Private journals/receipts and the tenant-partition guard are additive; no customer global account table replacement is introduced. See `docs/management/customer-membership-lifecycle.md`, `customer-tenant-status.md` and `customer-onboarding-policy.md` for consumer hook, provider and migration requirements.
