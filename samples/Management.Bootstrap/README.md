# Portable Management API bootstrap

This versioned sample runs a support API from IBeam NuGets and, optionally, three separate synthetic customer Identity API processes. The frontend requires only the running support API URL and a normal support login. No framework ProjectReferences or customer-specific backend are used.

This development bootstrap targets the upcoming `2.17.0` ownership release; stable `2.16.1` contains only the invite compatibility patch. Until 2.17.0 is released, provide a generated local feed and its exact `-PackageVersion`. For local validation, generate a matching feed using `scripts/Test-ManagementCustomerIdentityPackages.ps1` and supply `-PackageFeed <absolute-feed-path> -PackageVersion <actual-generated-version>`. With no feed supplied, startup restores published packages from NuGet.org. They do not publish packages or deploy services. Requirements: PowerShell 7, .NET 10, Node.js and Azurite Table (`npm install -g azurite@3.35.0`).

From this sample directory:

```powershell
./.scripts/start-enterprise-demo.ps1
./.scripts/test-enterprise-demo.ps1
./.scripts/stop-all.ps1 -Instance management-enterprise
```

The support API is `http://127.0.0.1:5155`; customer processes use 5255–5257; the private emulator uses 15122. All bind to loopback. Use `-ApiPort`, `-TablePort`, `-FirstTargetPort` and a new `-Instance` name for a separate stack. Existing listeners are never stopped by startup. Stop uses recorded PID, start time and executable marker checks, retains data/secrets, and stops only the processes belonging to that instance.

To run the same source from the temporary host placement, pass `-HostRoot C:/Projects/medpactech/IBeam/IBeam.ADMIN.API` to these scripts. The scripts remain versioned here; no repository rename or workspace-level script installation is required. This temporary host consumes the same NuGets and is not a dependency of the frontend. Its private instance directory is then under that host's `.local` folder.

Fresh setup creates a management organization, administrator and three support personas using the existing trusted bootstrap, support invitation acceptance, password and real MFA flows. It configures three synthetic app connections and explicit person/app customer-operation ceilings. The administrator and reader receive all customer operations; the limited persona has Atlas diagnostic errors only; the unassigned persona has no app assignment. User passwords, signing material, machine keys, customer credentials and storage configuration stay in protected `.local/{instance}` files. Support mail is under `outbox`; customer mail is under each `demo-*` subdirectory. No mail/config/setup HTTP endpoint exists. The tests read private mail as trusted local operators and submit the actual generated OTP to normal authentication endpoints.

Each customer process owns native Identity tables with a distinct `DemoCustomer*` prefix, a distinct realm/JWT issuer/audience/key, separate protected token keys and a scoped machine credential. Support Identity remains in the separate `DemoManagement*` namespace/container. The demo account is the isolated local devstoreaccount1 emulator. Prefixes provide logical separation in this fixture; real deployments should use the framework storage/credential configuration appropriate to their account and privilege boundaries. It seeds an active self-service owner, a disabled **membership** for another account, a disabled tenant and a pending invitation without creating its recipient account. Enterprise onboarding in the smoke uses an existing verified customer account and creates a real invitation/acceptance workflow. No customer business records, commercial module dependencies, support impersonation or global-account disable are introduced.

The explicit demo client implements the public Management customer-client port, validates the selected org/app/environment/realm/credential, checks real target discovery, issues normal RSA actor proofs and calls fixed management routes on the configured loopback customer process. Target machine checks, one-use mutation proofs, live support assignments, version checks, native OTP/acceptance, last-admin protection and JWT/session validation remain active. This Development-only adapter never replaces production network policy: normal connected targets use the framework client with approved public HTTPS, DNS/socket pinning and TLS. Diagnostics in demo mode remain synthetic through the existing public diagnostic ports.

Both modes enforce reciprocal MVC controller boundaries: support excludes native customer controllers, and customer mode excludes support Identity/portal controllers. Customer auth/acceptance endpoints live only in the customer processes. Native composition uses `AddIBeamIdentityApiWithCommunicationSender` after registering the private outbox; this shares the standard authentication/session pipeline and avoids installing unused Azure Communications providers. It does not disable options validation or OTP checks. Standard customer JWT access/refresh enforcement is installed before management membership/status capabilities are advertised.

Repeat startup preserves generated credentials, app IDs, user passwords, native status and revoked/changed access. Completed native seed and customer-connection setup markers prevent silently restoring removed keys or assignments. Normal startup does not reseed/retest customer connections before the target processes are running. If initial setup was interrupted, inspect the private instance logs; it keeps partial data and does not destructively roll back customer resources. For a clean reset, stop the stack and select a **new instance name and unused ports**; existing data is retained. To restore a grant intentionally, use the normal authorized assignment API with its current version. The old diagnostic-only `seed-demo.ps1 -RestoreAssignments` is an explicit diagnostic-fixture operation, not an automatic customer-access repair.

The smoke checks actual support and customer password/MFA, app/tenant/user/invitation visibility, enterprise creation and verified acceptance, authoritative completion, limited/anonymous/wrong-realm denials, and live assignment revocation. It temporarily removes one synthetic reader grant, proves the repeat trusted seed leaves it revoked, and explicitly restores the test's original grant using an authorized administrator and exact version. No tokens, passwords or machine keys are printed. The larger package-only matrix covers provider races, unknown mail/HTTP outcomes, role/status and issued-token enforcement, diagnostics scrubbing and ordinary auth regressions.

Give the frontend agent [the baseline application prompt](docs/baseline-app-prompt.md). It inventories exact support routes, envelopes, permissions, policy/role discovery, paging, idempotency, versions, pending/unknown outcomes and customer-owned acceptance. OpenAPI is available locally at `/openapi/v1.json`; it includes the support surface only. CORS allows the configured frontend origins and required Idempotency-Key/If-Match headers. Frontend implementation and production rollout are separate work.
